## 01 deslop-please: 에이전트가 만든 구조를 검사하는 린터

**핵심:** deslop-please는 문법이 아니라 **모듈 구조** 를 검사하는 Rust 린터입니다. 11월 22일에 만들어져 별 1,103개를 모았습니다(MIT, 2026-11-26 기준).

### 무엇을 잡아내나

README는 *A Philosophy of Software Design*의 원칙 하나를 기준으로 삼는다고 밝힙니다. **깊은 모듈, 좁은 인터페이스** 입니다. 규칙은 네 가지입니다.

| 규칙           | 잡아내는 상황                                                     |
|----------------|-------------------------------------------------------------------|
| module-cycle   | 모듈끼리 서로를 참조해 순환이 생긴 경우                           |
| tangle         | 부모와 자식 모듈이 서로를 알고 있어 분리가 안 되는 경우           |
| field-leak     | 구조체의 필드를 바깥 모듈이 직접 만지는 경우                      |
| shallow-module | 바깥에서 모듈 함수의 상당수를 직접 호출해, 인터페이스가 넓은 경우 |

### 왜 지금 이런 도구가 뜨나

에이전트가 쓴 코드는 대개 개별 함수 단위로는 잘 동작합니다. 문제는 **사이** 에서 생깁니다. 필요한 값을 그때그때 바깥에서 꺼내 쓰다 보면 필드가 새어 나가고, 모듈끼리 서로를 참조하게 됩니다. 기존 린터는 이런 구조 문제를 보지 않습니다. README가 AGENTS.md에 넣을 문구를 함께 제안하는 것도 이 때문입니다. 기계적으로 숨기지 말고 구조를 다시 생각하라는 지시를 에이전트에게 주는 방식입니다.

### 직접 해보기

STEP 1

cargo로 설치

STEP 2

저장소 루트에서 실행

STEP 3

기존 경고는 allow 파일로 분리

STEP 4

AGENTS.md에 검사 규칙 추가

▶ 설치하고 실행하기 (Rust 프로젝트 루트에서)

```
cargo install deslop-please
deslop-please
```

▶ 기존 코드의 경고는 일단 분리해 두기

```
# 현재 상태를 allow 파일로 기록
deslop-please --update-allow .deslop-please.allow

# 이후에는 새로 생긴 것만 보인다
deslop-please --allow .deslop-please.allow
```

💡 팁

이미 커진 프로젝트에 처음 돌리면 경고가 수백 개 나올 수 있습니다. 전부 고치려 하지 말고 allow 파일로 기준선을 잡은 뒤, **새로 생기는 것만** 막는 방식이 현실적입니다.

## 02 skill-distill: 좋은 세션을 작은 모델용 스킬로

**핵심:** skill-distill은 프런티어 모델(교사)이 잘 끝낸 세션을 읽고, 오픈웨이트 모델(학생)이 같은 작업을 해내도록 스킬을 써 주는 도구입니다. 11월 21일 생성, 별 819개입니다(MIT, 2026-11-26 기준).

### 루프가 도는 방식

README가 적은 절차는 다섯 단계입니다. 교사가 세션을 읽고 스킬을 쓰고, 학생을 tmux에서 깨끗한 시작 상태로 띄우고, 결과를 기준 결과와 비교하고, 학생이 **처음 어긋난 지점** 을 찾아 그 부분의 스킬을 고치고, 다시 돌립니다.

| 규칙      | 내용                                                                                        |
|-----------|---------------------------------------------------------------------------------------------|
| 동일 조건 | 학생은 교사와 같은 프롬프트, 깨끗한 시작 상태, 스킬만 받습니다                              |
| 정답 금지 | 스킬에 완성된 결과물이나 그것을 그대로 쓰는 스크립트를 넣을 수 없습니다                     |
| 3회 시험  | 스킬 버전마다 3회씩 돌립니다. 한 번 성공은 근거가 되지 않습니다                             |
| 검사 검증 | 검사 기준은 먼저 기준 결과에 적용해 봅니다. 기준 결과에서 실패하는 검사는 잘못된 검사입니다 |
| 최종 판단 | 사람이 양쪽 결과를 비교하고 수락해야 끝납니다                                               |

### 왜 흥미로운가

"작은 모델이 큰 모델을 못 따라간다"는 말은 대개 모델 성능 문제로 다뤄집니다. 이 도구는 질문을 바꿉니다. **지시가 충분히 구체적이었다면 작은 모델도 할 수 있는가** 입니다. 성공하면 결과물이 두 개 남습니다. 재사용 가능한 운영 스킬과, 특정 작업·모델·하네스 한 쌍에 맞춘 스킬입니다.

▶ 설치 (Claude Code 또는 Codex에 스킬로 연결)

```
git clone https://github.com/sybil-solutions/skill-distill
ln -s "$PWD/skill-distill/skills/skill-distill" ~/.claude/skills/skill-distill   # Claude Code
ln -s "$PWD/skill-distill/skills/skill-distill" ~/.agents/skills/skill-distill   # Codex
```

▶ 학생이 일하는 모습 보기

```
tmux attach -t distill-<작업이름>
```

📌 알아둘 점

요구 사항은 tmux, git, Python 3.10 이상, 그리고 학생 하네스가 모델에 연결된 상태입니다. 하네스별 어댑터의 검증 수준은 서로 다릅니다. README는 omp를 테스트 완료로, pi와 opencode를 미검증으로 적어 두었습니다.

[출처 · GitHub · skill-distill ↗](https://github.com/sybil-solutions/skill-distill)

## 03 llm.asm: 어셈블리만으로 만든 LLM 추론

**핵심:** llm.asm은 Qwen3-0.6B 추론, 부팅 가능한 베어메탈 OS, 미니 GPT 학습기를 모두 x86-64 어셈블리로만 구현한 프로젝트입니다. 11월 25일 생성, 하루 만에 별 849개를 모았습니다(MIT, 2026-11-26 기준).

| 프로젝트    | 바이너리 크기 | 내용                                                            |
|-------------|---------------|-----------------------------------------------------------------|
| 추론        | 14,712 B      | Qwen3-0.6B(Q8_0) 실행, BPE 토크나이저 내장, 멀티턴 KV 캐시 REPL |
| 베어메탈 OS | 24,252 B      | 리눅스·윈도우 없이 부팅해 채팅. 부팅 74~94 ms                   |
| 학습기      | 32,944 B      | FP32 미니 GPT 학습과 샘플링, 브라유 문자 TUI                    |

README가 적은 성능은 AMD EPYC 7642, CPU 전용(-ngl 0), 같은 모델 기준입니다. 1스레드 20.70 tok/s, 16스레드 121.86 tok/s, 40스레드에서 125.86 tok/s이며, 같은 조건의 llama.cpp 대비 **1.18~1.36배** 로 적어 두었습니다. 의존성은 C, C++, Rust, libc 없이 0이고, 전체 어셈블리 코드는 17,252줄이라고 밝힙니다.

llama.cpp (16스레드)

103.03 tok/s

llm.asm (16스레드)

121.86 tok/s

### 실용적인가

실무에 바로 쓸 도구는 아닙니다. 모델 하나, CPU 하나에 맞춘 구현이고 어셈블리라 이식성도 없습니다. 다만 **런타임 오버헤드가 얼마나 큰지** 를 보여 주는 참고 자료로는 가치가 있습니다. 수치는 모두 저자가 올린 것이므로, 인용할 때는 재현 조건(CPU 모델, 스레드 수, 양자화 방식)을 함께 적는 편이 안전합니다.

[출처 · GitHub · llm.asm ↗](https://github.com/alesha-pro/llm.asm)

## 자주 묻는 질문

### Q. deslop-please는 기존 린터와 무엇이 다른가요?

clippy 같은 일반 린터가 문법과 관용구를 보는 반면, deslop-please는 모듈 구조를 봅니다. 규칙은 module-cycle, tangle, field-leak, shallow-module 네 가지로, 모듈 순환이나 구조체 필드가 바깥으로 새는 상황을 잡아냅니다. 2026년 11월 26일 기준 별 1,103개이며 MIT 라이선스입니다.

### Q. skill-distill에서 스킬 하나를 몇 번 시험하나요?

README 기준으로 스킬 버전마다 3회씩 돌립니다. 한 번 성공한 결과는 근거로 보지 않기 때문입니다. 또한 검사 기준을 먼저 기준 결과에 적용해 보고, 기준 결과에서 실패하는 검사는 잘못된 검사로 취급합니다. 최종 수락은 사람이 합니다.

### Q. llm.asm의 성능 수치는 믿을 만한가요?

README에 적힌 수치는 저자가 AMD EPYC 7642에서 CPU 전용으로 측정한 값입니다. 16스레드에서 llm.asm 121.86 tok/s, llama.cpp 103.03 tok/s로 1.18배라고 적혀 있습니다. 제3자 검증 결과는 아직 없으므로, 인용할 때는 측정 환경을 함께 밝히는 편이 좋습니다.

## 정리

**deslop-please:** 모듈 구조를 보는 Rust 린터. allow 파일로 기준선을 잡고 새 경고만 막는 방식이 현실적입니다.

**skill-distill:** 좋은 세션을 오픈웨이트 모델용 스킬로 증류. 버전마다 3회 시험, 최종 판단은 사람.

**llm.asm:** 어셈블리만으로 만든 LLM 추론. 실무용은 아니지만 런타임 오버헤드의 크기를 보여 줍니다.
