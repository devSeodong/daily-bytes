# OSI 7계층 완벽 정리 - 택배 비유로 이해하는 계층별 역할, 프로토콜, 장비, 캡슐화

> 💻 **Computer Science** · 2026-11-28 · 📝 [티스토리에서 보기](https://dongseodong.tistory.com/84)

![대표 이미지](assets/2026-11-28-osi-7-layer.png)

네트워크 공부를 시작하면 가장 먼저 만나는 개념이 **OSI 7계층** 입니다. 그런데 "물리, 데이터링크, 네트워크, 전송, 세션, 표현, 응용"을 외우는 것만으로는 실제 통신이 어떻게 흘러가는지 잘 그려지지 않습니다. 이 글에서는 먼저 **택배 비유** 로 전체 흐름을 잡고, 그다음 각 계층의 역할, 주소, 장비, 프로토콜, 헤더 구조, 그리고 직접 확인해 볼 수 있는 명령어까지 최대한 자세히 정리합니다.

로드밸런서의 L4, L7 같은 용어도 결국 이 계층 번호에서 나옵니다. 이어지는 글 「로드밸런서 종류를 OSI 7계층으로 이해하기」를 읽기 전에 이 글로 기초를 다져 두시면 좋습니다.

TL;DR · 한눈에 보기

1 **OSI 7계층** 은 ISO가 1984년에 표준으로 정한 네트워크 통신의 7단계 참조 모델이며, 각 계층은 바로 아래 계층의 서비스만 이용해 자기 일만 합니다.

3 실제 인터넷은 4계층짜리 **TCP/IP 모델** 로 움직이지만, 장애 분석이나 장비 분류(L2 스위치, L4·L7 로드밸런서)에는 여전히 OSI 번호를 씁니다.

## 01 OSI 7계층이란 무엇인가

**한 줄 답:** OSI(Open Systems Interconnection) 7계층은 서로 다른 회사의 컴퓨터와 장비가 통신할 수 있도록, 통신 과정을 7개의 역할로 나눠 정의한 국제 표준 참조 모델입니다. ISO 7498로 1984년에 처음 발표되었고, 현재 판은 ISO/IEC 7498-1:1994입니다.

### 왜 계층을 나눴을까

1970년대에는 IBM의 SNA, DEC의 DECnet처럼 회사마다 통신 방식이 달라서, 다른 회사 장비끼리는 대화가 되지 않았습니다. 그래서 "어떤 회사 제품이든 이 역할 분담만 지키면 서로 통한다"는 공통 기준이 필요했고, 그 결과물이 OSI 모델입니다.

계층을 나누면 다음과 같은 장점이 생깁니다.

| 장점 | 설명 | 예시 |
|----|----|----|
| 독립성 | 한 계층을 바꿔도 다른 계층은 그대로 둘 수 있습니다. | 유선 랜을 와이파이로 바꿔도 브라우저와 HTTP는 그대로 동작합니다. |
| 표준화 | 계층 사이의 약속(인터페이스)만 지키면 여러 제조사 제품을 섞어 쓸 수 있습니다. | A사 랜카드 + B사 스위치 + C사 라우터 |
| 문제 위치 파악 | 어느 계층에서 막혔는지 범위를 좁혀 가며 장애를 찾을 수 있습니다. | "ping은 되는데 웹이 안 열린다" → 3계층은 정상, 4계층 이상을 확인 |
| 학습과 설계 | 복잡한 통신을 작은 역할로 쪼개서 이해하고 설계할 수 있습니다. | 장비를 L2, L3, L4, L7로 분류 |

### OSI 7계층과 TCP/IP 4계층

OSI는 "이렇게 나누면 좋다"는 **참조 모델** 이고, 실제 인터넷은 **TCP/IP 모델** (RFC 1122 기준 링크, 인터넷, 전송, 응용 4계층)로 구현되어 있습니다. TCP/IP는 OSI의 5·6·7계층을 하나의 응용 계층으로 묶고, 1·2계층을 링크 계층으로 묶습니다.

OSI 7계층

7 응용 (Application)

6 표현 (Presentation)

5 세션 (Session)

4 전송 (Transport)

3 네트워크 (Network)

2 데이터링크 (Data Link)

1 물리 (Physical)

TCP/IP 4계층

응용 (HTTP, DNS, TLS, SSH …)

전송 (TCP, UDP)

인터넷 (IP, ICMP)

링크 (이더넷, 와이파이 …)

그래서 현업에서 "L3 장비", "L7 로드밸런서"라고 할 때의 숫자는 OSI 번호이고, 실제로 오가는 프로토콜은 TCP/IP 묶음이라고 이해하시면 됩니다.

## 02 택배 비유로 한 번에 이해하기

**한 줄 답:** 7계층은 "선물을 준비하고 → 포장하고 → 받는 사람과 약속하고 → 상자에 번호를 붙이고 → 주소로 경로를 정하고 → 구간마다 트럭으로 옮기고 → 실제 도로를 달리는" 택배 과정과 닮았습니다.

서울에 사는 내가 부산에 사는 친구에게 생일 선물과 편지를 택배로 보낸다고 생각해 보겠습니다. 보내는 쪽은 7계층에서 1계층으로 내려가고, 받는 쪽은 1계층에서 7계층으로 올라갑니다.

7 응용 ✉️ **편지 쓰기** · 무엇을 보낼지 정하고 내용을 작성합니다.

6 표현 🎁 **포장하기** · 친구가 읽을 수 있는 언어로 쓰고, 진공 압축하고, 봉인 스티커(암호화)를 붙입니다.

5 세션 📞 **미리 통화하기** · "지금부터 보낼게, 다 받으면 알려 줘"라고 대화를 열고, 끝나면 닫습니다.

4 전송 📦 **상자 나누고 번호 붙이기** · 큰 짐을 1/3, 2/3, 3/3 상자로 나누고 "몇 호(포트)" 받는 사람을 적고, 도착 확인(등기)을 받습니다.

3 네트워크 🗺️ **주소 보고 경로 정하기** · 도로명 주소(IP)를 보고 서울 허브 → 대전 허브 → 부산 허브 경로를 고릅니다.

2 데이터링크 🚚 **다음 거점까지 운반** · "서울 허브에서 대전 허브까지" 한 구간만 책임지는 트럭 기사와 구간 송장(MAC)입니다.

1 물리 🛣️ **도로와 바퀴** · 실제로 트럭이 달리는 도로, 전선, 빛, 전파입니다.

여기서 꼭 기억할 점이 두 가지 있습니다.

**첫째, 주소가 두 종류입니다.** 택배 상자에 적힌 최종 목적지 주소(IP)는 서울에서 부산까지 바뀌지 않지만, 구간마다 붙는 송장(MAC)은 거점을 지날 때마다 새로 붙습니다. 이것이 3계층 주소와 2계층 주소의 차이입니다.

**둘째, 각 계층은 자기 일만 합니다.** 트럭 기사(2계층)는 상자 안에 편지가 들었는지 몰라도 되고, 편지를 쓴 나(7계층)는 어떤 도로로 가는지 몰라도 됩니다. 이 분업 덕분에 한 부분을 바꿔도 전체가 무너지지 않습니다.

💡 비유의 한계도 알아 두기

택배 비유는 흐름을 잡는 용도입니다. 실제로는 세션·표현 계층의 일을 응용 프로그램이 직접 하는 경우가 많고, TLS처럼 어느 한 계층에 딱 들어맞지 않는 프로토콜도 있습니다. 아래 계층별 설명에서 실제 동작을 함께 보겠습니다.

## 03 캡슐화와 역캡슐화: 헤더가 붙고 떨어지는 과정

**한 줄 답:** 데이터가 아래 계층으로 내려갈 때마다 그 계층의 제어 정보(헤더, 때로는 트레일러)가 앞뒤에 붙는 것을 캡슐화라고 하고, 받는 쪽에서 하나씩 떼어 내는 것을 역캡슐화라고 합니다.

각 계층에서 다루는 데이터 덩어리를 **PDU** (Protocol Data Unit)라고 부르며, 계층마다 이름이 다릅니다.

| 계층 | PDU 이름 | 붙는 정보 | 대표 크기 |
|----|----|----|----|
| 7·6·5 | 데이터 (메시지) | HTTP 헤더, 인코딩·압축·암호화 정보 | 내용에 따라 다름 |
| 4 전송 | 세그먼트 (TCP) / 데이터그램 (UDP) | 출발·도착 포트, 순서 번호, 확인 번호, 체크섬 | TCP 헤더 20~60바이트, UDP 헤더 8바이트 |
| 3 네트워크 | 패킷 | 출발·도착 IP, TTL, 프로토콜 번호 | IPv4 헤더 20~60바이트, IPv6 기본 헤더 40바이트 |
| 2 데이터링크 | 프레임 | 출발·도착 MAC, EtherType, FCS(오류 검사) | 이더넷 헤더 14바이트 + FCS 4바이트 |
| 1 물리 | 비트 | 프리앰블 등 신호 동기화 정보 | 0과 1의 신호 |

캡슐화 모습 (위에서 아래로 내려갈수록 바깥 포장이 늘어납니다)

데이터 (HTTP 요청)

TCP 헤더 데이터

IP 헤더 TCP 헤더 데이터

이더넷 헤더 IP TCP 데이터 FCS

### MTU와 MSS: 한 번에 실을 수 있는 양

이더넷 한 프레임에 실을 수 있는 최대 데이터 크기를 **MTU** (Maximum Transmission Unit)라고 하며, 일반적인 이더넷은 1,500바이트입니다. 여기서 IPv4 헤더 20바이트와 TCP 헤더 20바이트를 빼면, TCP가 한 세그먼트에 실을 수 있는 실제 데이터인 **MSS** (Maximum Segment Size)는 1,460바이트가 됩니다.

이더넷 MTU

1,500B

− IPv4 + TCP 헤더

40B

= TCP MSS

1,460B

VPN이나 터널을 쓰면 바깥에 헤더가 더 붙어서 실을 수 있는 양이 줄어듭니다. "작은 요청은 되는데 큰 파일만 멈춘다"는 증상이 MTU 문제인 경우가 많은 이유입니다.

▶ 내 PC의 MTU 확인하기 (Linux / macOS)

```
# Linux: 인터페이스별 mtu 값 확인
ip link show

# macOS
ifconfig en0 | grep mtu

# 조각내지 않고(DF) 1472바이트 데이터를 보내 경로 MTU 확인 (1472 + ICMP 8 + IP 20 = 1500)
ping -M do -s 1472 8.8.8.8      # Linux
ping -D -s 1472 8.8.8.8         # macOS
```

## 04 1계층 물리 계층 (Physical Layer)

**한 줄 답:** 물리 계층은 0과 1의 비트를 전기 신호, 빛, 전파로 바꿔 실제 매체 위로 보내고 받는 계층입니다. 데이터의 의미나 주소는 전혀 모르고, 신호만 다룹니다.

### 하는 일

| 항목 | 내용 |
|----|----|
| 신호 변환 | 비트를 전압의 높낮이, 빛의 켜짐과 꺼짐, 전파의 위상·진폭 변화로 바꿉니다. 이를 **인코딩·변조** 라고 합니다. 예를 들어 10BASE-T 이더넷은 맨체스터 인코딩을, 100BASE-TX는 4B/5B 부호화를 씁니다. |
| 매체 규격 | 케이블 종류, 커넥터 모양(RJ-45, LC), 핀 배열, 전압, 최대 길이를 정합니다. |
| 전송 속도와 동기화 | 초당 몇 비트를 보낼지(bps), 보내는 쪽과 받는 쪽의 박자를 어떻게 맞출지 정합니다. |
| 전송 방향 | **단방향** (simplex, TV 방송), **반이중** (half-duplex, 무전기), **전이중** (full-duplex, 전화)이 있습니다. 요즘 스위치 포트는 대부분 전이중입니다. |

### 대표 매체와 장비

| 매체·장비 | 특징 |
|----|----|
| UTP 케이블 | Cat5e는 1Gbps를 100m까지, Cat6은 10Gbps를 약 55m까지, Cat6a는 10Gbps를 100m까지 지원합니다. |
| 광케이블 | 빛으로 신호를 보내 수 km 이상 멀리, 전자기 간섭 없이 보낼 수 있습니다. 데이터센터와 통신사 구간에서 씁니다. |
| 무선 (전파) | 와이파이의 물리 계층은 IEEE 802.11 규격이 정하며, 2.4GHz·5GHz·6GHz 대역을 씁니다. |
| 리피터 | 약해진 신호를 다시 증폭해 더 멀리 보냅니다. |
| 허브 | 들어온 신호를 모든 포트로 그대로 복사합니다. 누구에게 가는지 모르기 때문에 충돌이 많아 지금은 거의 스위치로 대체되었습니다. |

📌 장애가 1계층이면

랜선이 빠졌거나, 포트 불빛(링크 LED)이 꺼졌거나, 속도·이중 모드가 맞지 않는 경우입니다. 위 계층을 아무리 봐도 소용없으므로, 장애 분석은 늘 "선이 꽂혀 있고 링크가 올라왔나"부터 확인합니다.

▶ 링크 상태와 협상 속도 확인 (Linux)

```
# 링크가 올라왔는지(state UP), 속도·이중 모드 확인
ip link show eth0
sudo ethtool eth0 | grep -E "Speed|Duplex|Link detected"
```

## 05 2계층 데이터링크 계층 (Data Link Layer)

**한 줄 답:** 데이터링크 계층은 같은 네트워크(같은 스위치, 같은 와이파이) 안에서 바로 옆 장비까지 프레임을 오류 없이 전달하는 계층이며, **MAC 주소** 로 상대를 구분합니다.

### MAC 주소

MAC 주소는 랜카드마다 부여된 48비트(6바이트) 주소로, `3c:22:fb:12:ab:cd`처럼 16진수로 씁니다. 앞 24비트는 제조사 번호(OUI), 뒤 24비트는 제조사가 붙인 일련번호입니다. 택배 비유의 "구간 송장"처럼 라우터를 하나 지날 때마다 출발·도착 MAC이 새로 바뀝니다.

### 이더넷 프레임 구조

| 필드 | 크기 | 설명 |
|----|----|----|
| 프리앰블 + SFD | 7 + 1바이트 | 받는 쪽이 박자를 맞추고 프레임 시작을 알아채게 하는 신호입니다 (물리 계층에서 처리). |
| 도착 MAC | 6바이트 | 받을 장비의 MAC 주소입니다. `ff:ff:ff:ff:ff:ff`는 전체에게 보내는 브로드캐스트입니다. |
| 출발 MAC | 6바이트 | 보내는 장비의 MAC 주소입니다. |
| EtherType | 2바이트 | 안에 든 3계층 프로토콜 종류입니다. `0x0800` IPv4, `0x86DD` IPv6, `0x0806` ARP. |
| 데이터 (페이로드) | 46~1,500바이트 | IP 패킷이 들어갑니다. 46바이트보다 작으면 채움(padding)을 넣습니다. |
| FCS | 4바이트 | CRC-32 값으로, 받는 쪽이 계산해 다르면 프레임을 버립니다. 고치지는 않고 **검출만** 합니다. |

### 스위치는 어떻게 길을 아는가

2계층의 대표 장비인 **스위치** 는 포트로 들어온 프레임의 출발 MAC을 보고 "이 MAC은 3번 포트에 있다"를 **MAC 주소 테이블** 에 적어 둡니다(학습). 이후 그 MAC으로 가는 프레임은 3번 포트로만 보냅니다(포워딩). 아직 모르는 주소라면 모든 포트로 보내고(플러딩) 답장을 보며 배웁니다. 허브와 달리 필요한 포트로만 보내므로 충돌이 사라집니다.

STEP 1 · 학습

A가 1번 포트로 프레임을 보내면 "A = 1번 포트"를 테이블에 적습니다.

STEP 2 · 플러딩

도착지 B를 아직 모르면 1번을 뺀 모든 포트로 내보냅니다.

STEP 3 · 포워딩

B가 답하면 "B = 4번 포트"를 배우고, 다음부터는 4번으로만 보냅니다.

### 2계층의 다른 중요한 기술

| 기술 | 하는 일 |
|----|----|
| ARP (RFC 826) | "IP가 192.168.0.1인 장비의 MAC 주소는 무엇인가요?"를 브로드캐스트로 묻고 답을 받아 IP와 MAC을 짝지어 줍니다. 2계층과 3계층 사이를 잇기 때문에 2.5계층이라고 부르기도 합니다. |
| VLAN (IEEE 802.1Q) | 스위치 한 대를 논리적으로 여러 네트워크로 나눕니다. 프레임에 4바이트 태그를 넣으며, VLAN ID는 12비트라 1~4094번을 쓸 수 있습니다. |
| STP (IEEE 802.1D) | 스위치를 고리 모양으로 연결했을 때 브로드캐스트가 끝없이 도는 문제(루프)를 막기 위해 일부 포트를 막습니다. |
| 매체 접근 제어 | 여럿이 한 매체를 쓸 때 누가 언제 보낼지 정합니다. 옛 이더넷은 CSMA/CD, 와이파이는 CSMA/CA를 씁니다. |
| LLC / MAC 부계층 | IEEE는 2계층을 위쪽 LLC(논리 링크 제어)와 아래쪽 MAC(매체 접근 제어)으로 다시 나눕니다. |

▶ ARP 캐시와 내 MAC 주소 확인

```
# 내 랜카드의 MAC 주소 (link/ether 뒤의 값)
ip link show

# 지금까지 알아낸 IP ↔ MAC 짝 (ARP 캐시)
ip neigh          # Linux
arp -a            # macOS, Windows
```

## 06 3계층 네트워크 계층 (Network Layer)

**한 줄 답:** 네트워크 계층은 서로 다른 네트워크를 건너 최종 목적지까지 패킷을 보내는 계층입니다. **IP 주소** 로 목적지를 정하고, **라우터** 가 라우팅 테이블을 보며 다음에 보낼 곳을 고릅니다.

### IP 주소와 서브넷

IPv4 주소는 32비트로 `192.168.0.10`처럼 씁니다. 앞부분은 네트워크 번호, 뒷부분은 그 안의 장비 번호이며, 어디까지가 네트워크인지를 **서브넷 마스크** 또는 **CIDR 표기** (`/24`)로 나타냅니다. `192.168.0.0/24`는 앞 24비트가 네트워크라는 뜻으로, 장비에 쓸 수 있는 주소는 254개입니다(네트워크 주소와 브로드캐스트 주소 제외).

IPv4 주소가 약 43억 개뿐이라 부족해졌고, 그래서 128비트 주소를 쓰는 **IPv6** (`2001:db8::1`)와, 사설 IP 여러 개를 공인 IP 하나로 바꿔 주는 **NAT** 가 널리 쓰입니다.

### IPv4 헤더의 주요 필드

| 필드 | 설명 |
|----|----|
| 버전 / 헤더 길이 | IPv4이면 4, 헤더 길이는 보통 20바이트입니다. |
| TTL (Time To Live) | 라우터를 하나 지날 때마다 1씩 줄고, 0이 되면 버려집니다. 길을 잃은 패킷이 영원히 떠도는 것을 막습니다. 기본값은 Linux·macOS 64, Windows 128입니다. |
| 프로토콜 | 안에 든 4계층 종류입니다. 6 = TCP, 17 = UDP, 1 = ICMP. |
| 출발 / 도착 IP | 처음부터 끝까지 바뀌지 않는 주소입니다 (NAT를 지날 때는 예외). |
| 식별자 / 플래그 / 조각 오프셋 | 패킷이 다음 구간의 MTU보다 크면 잘게 나누는데(단편화), 받는 쪽이 다시 합칠 수 있게 하는 정보입니다. DF 플래그가 켜져 있으면 나누지 않고 버린 뒤 ICMP로 알립니다. |
| 헤더 체크섬 | 헤더가 깨졌는지 검사합니다 (IPv6에서는 없어졌습니다). |

### 라우팅: 다음 거점 고르기

라우터는 패킷을 받으면 도착 IP를 보고 라우팅 테이블에서 **가장 길게 일치하는 경로** (Longest Prefix Match)를 골라 다음 라우터(next hop)로 보냅니다. 이때 2계층 프레임은 새로 만들고(MAC 교체), 3계층 IP는 그대로 둡니다. 맞는 경로가 없으면 기본 경로(`0.0.0.0/0`, 기본 게이트웨이)로 보냅니다.

라우팅 테이블은 사람이 직접 넣거나(정적 라우팅), OSPF·BGP 같은 **라우팅 프로토콜** 로 라우터끼리 정보를 주고받아 자동으로 채웁니다. 인터넷 전체는 통신사들이 BGP로 서로 경로를 알려 주며 연결되어 있습니다.

### ICMP: 네트워크 계층의 알림 메시지

**ICMP** 는 "목적지에 갈 수 없음", "TTL 만료" 같은 오류와 상태를 알려 주는 프로토콜입니다. `ping`은 ICMP Echo 요청·응답을, `traceroute`는 TTL을 1, 2, 3…으로 늘려 보내며 각 라우터가 돌려주는 "TTL 만료" 메시지로 경로를 알아냅니다.

▶ 라우팅 테이블과 경로 확인

```
# 내 라우팅 테이블 (default via ... 가 기본 게이트웨이)
ip route              # Linux
netstat -rn           # macOS

# 목적지까지 거치는 라우터 목록
traceroute google.com     # Linux, macOS
tracert google.com        # Windows

# 3계층 도달 여부
ping -c 4 8.8.8.8
```

## 07 4계층 전송 계층 (Transport Layer)

**한 줄 답:** 전송 계층은 목적지 컴퓨터 안의 **어떤 프로그램** 에게 데이터를 줄지 **포트 번호** 로 정하고, 필요하면 순서 보장, 재전송, 흐름 제어, 혼잡 제어로 믿을 수 있는 전달을 책임지는 계층입니다. 대표 프로토콜은 TCP와 UDP입니다.

### 포트 번호

IP 주소가 "건물 주소"라면 포트는 "몇 호"입니다. 16비트라 0~65535를 쓰며, 0~1023은 잘 알려진 포트(well-known port)로 HTTP 80, HTTPS 443, SSH 22, DNS 53 등이 정해져 있습니다. **출발 IP, 출발 포트, 도착 IP, 도착 포트, 프로토콜** 다섯 가지를 묶어 5-튜플이라고 하며, 이것으로 연결 하나를 구분합니다. L4 로드밸런서가 바로 이 정보를 보고 서버를 고릅니다.

### TCP와 UDP 비교

| 구분 | TCP | UDP |
|----|----|----|
| 연결 | 연결 지향 (3-way handshake로 연결 후 전송) | 비연결 (바로 전송) |
| 신뢰성 | 순서 번호, 확인 응답(ACK), 재전송으로 보장 | 보장 안 함 (필요하면 응용이 직접 처리) |
| 흐름·혼잡 제어 | 있음 (수신 윈도우, 혼잡 윈도우) | 없음 |
| 헤더 크기 | 20~60바이트 | 8바이트 |
| 속도·지연 | 상대적으로 느림 | 빠름 |
| 쓰임 | 웹(HTTP/1.1, HTTP/2), 이메일, SSH, 파일 전송 | DNS 조회, 실시간 영상·음성, 게임, QUIC(HTTP/3) |
| 표준 | RFC 9293 (2022년 정리판) | RFC 768 |

### TCP 3-way handshake와 4-way 종료

① SYN

클라이언트: "연결하고 싶습니다. 제 시작 번호는 x입니다."

② SYN + ACK

서버: "좋습니다. x+1부터 기다리겠습니다. 제 시작 번호는 y입니다."

③ ACK

클라이언트: "y+1부터 기다리겠습니다." 이제 데이터를 주고받습니다.

종료할 때는 양쪽이 각자 FIN을 보내고 ACK를 받는 **4-way handshake** 를 합니다. 먼저 끊은 쪽은 늦게 도착할 패킷을 대비해 잠시 `TIME_WAIT` 상태로 기다립니다. 서버에 `TIME_WAIT` 연결이 수만 개 쌓이는 현상은 짧은 연결을 많이 맺을 때 자주 보이며, Keep-Alive나 커넥션 풀로 줄일 수 있습니다.

### 흐름 제어와 혼잡 제어

| 기능 | 누구를 보호하나 | 방법 |
|----|----|----|
| 흐름 제어 | 받는 컴퓨터 | 받는 쪽이 "지금 이만큼 받을 수 있다"(수신 윈도우)를 알려 주면 보내는 쪽이 그 이상 보내지 않습니다 (슬라이딩 윈도우). |
| 혼잡 제어 | 중간 네트워크 | 처음에는 조금씩 보내다가 두 배씩 늘리고(slow start), 손실이 생기면 줄입니다. Linux 기본 알고리즘은 CUBIC이고, 구글이 만든 BBR도 많이 씁니다. |
| 재전송 | 데이터 자체 | 일정 시간 ACK가 없거나 같은 ACK가 세 번 오면(빠른 재전송) 다시 보냅니다. |

📌 QUIC은 몇 계층일까

HTTP/3가 쓰는 QUIC(RFC 9000)은 UDP 위에서 동작하지만, 연결 관리·재전송·혼잡 제어·암호화(TLS 1.3)를 스스로 합니다. 즉 4계층의 일을 응용 쪽에서 다시 구현한 형태라, 하나의 OSI 계층에 딱 맞추기 어렵습니다.

▶ 열린 포트와 TCP 연결 상태 보기

```
# 듣고 있는(LISTEN) TCP 포트와 프로세스
sudo ss -tlnp            # Linux
sudo lsof -iTCP -sTCP:LISTEN -n -P   # macOS

# 연결 상태별 개수 (ESTAB, TIME-WAIT …)
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c

# 특정 포트로 4계층 연결이 되는지만 확인
nc -vz example.com 443
```

## 08 5계층 세션 계층 (Session Layer)

**한 줄 답:** 세션 계층은 두 프로그램 사이의 대화(세션)를 열고, 유지하고, 끝내는 일을 맡습니다. 대화 방향 조절과 중간 저장(동기점)도 이 계층의 역할입니다.

| 역할 | 설명 | 비유 |
|----|----|----|
| 세션 수립·유지·종료 | 통신을 시작하기 전에 인증 등으로 대화를 열고, 다 끝나면 정리합니다. | "지금부터 보낼게" / "다 받았어, 끊을게" |
| 대화 제어 | 양쪽이 동시에 말할지(전이중), 번갈아 말할지(반이중) 정합니다. | 무전기처럼 "오버" |
| 동기점 (체크포인트) | 긴 전송 중간에 표시를 남겨, 끊기면 처음이 아니라 마지막 동기점부터 다시 보냅니다. | "10번 상자까지는 받았어" |

실제 TCP/IP에는 세션 계층이 따로 없고, 이 기능은 응용 프로그램이나 프로토콜 안에 녹아 있습니다. 흔히 세션 계층의 예로 드는 것은 다음과 같습니다.

| 예시 | 세션 계층 성격 |
|----|----|
| RPC, NetBIOS 세션 서비스 | 원격 호출이나 파일 공유를 위한 대화를 열고 관리합니다. |
| TLS 세션 재개 | 한 번 맺은 암호 세션 정보를 기억해 다음 연결 때 협상 단계를 줄입니다. |
| 이어받기 다운로드 | HTTP `Range` 요청으로 끊긴 지점부터 다시 받는 것은 동기점과 같은 발상입니다. |
| 웹 로그인 세션 | 쿠키의 세션 ID로 "같은 사용자와의 대화"를 이어 가는 것은 7계층 기능이지만, 세션 개념을 이해하기 좋은 예입니다. |

⚠ 헷갈리기 쉬운 점

웹 개발에서 말하는 "세션"(서버가 로그인 상태를 기억하는 것)과 OSI 5계층의 세션은 이름만 같고 층위가 다릅니다. 다만 "여러 요청을 하나의 대화로 묶는다"는 생각은 같습니다. 이 개념은 로드밸런서의 **세션 유지(sticky session)** 에서 다시 나옵니다.

## 09 6계층 표현 계층 (Presentation Layer)

**한 줄 답:** 표현 계층은 데이터를 상대방이 이해할 수 있는 형식으로 바꾸는 계층입니다. **문자 인코딩, 데이터 형식 변환(직렬화), 압축, 암호화** 가 이 계층의 일입니다.

| 기능 | 설명 | 실제 예 |
|----|----|----|
| 문자 인코딩 | 글자를 바이트로, 바이트를 글자로 바꿉니다. 양쪽 인코딩이 다르면 한글이 깨집니다. | UTF-8, EUC-KR, ASCII |
| 직렬화 | 프로그램 안의 객체를 전송할 수 있는 바이트열로 바꾸고 되돌립니다. | JSON, XML, Protocol Buffers, ASN.1 |
| 압축 | 보낼 양을 줄입니다. | gzip, Brotli, zstd |
| 암호화 | 중간에서 엿볼 수 없게 바꿉니다. | TLS의 암호화 부분 |
| 미디어 형식 | 이미지·영상 데이터의 형식을 정합니다. | JPEG, PNG, MP4 |

HTTP에서는 이 일을 헤더로 알려 줍니다. `Content-Type: application/json; charset=utf-8`는 "JSON 형식이고 UTF-8로 인코딩했다", `Content-Encoding: gzip`은 "gzip으로 압축했다"는 뜻입니다.

▶ 표현 계층 정보 직접 보기 (압축과 형식)

```
# 응답 헤더만 보고, 서버가 어떤 형식·압축으로 보내는지 확인
curl -sI -H "Accept-Encoding: gzip, br" https://www.google.com | grep -iE "content-type|content-encoding"

# 같은 문자열의 UTF-8 / EUC-KR 바이트 비교
printf '한글' | xxd
printf '한글' | iconv -f UTF-8 -t EUC-KR | xxd
```

📌 TLS는 몇 계층일까

TLS는 TCP(4계층) 위, HTTP(7계층) 아래에서 암호화를 맡으므로 흔히 "6계층 기능"으로 설명합니다. 다만 핸드셰이크로 세션을 맺는 부분은 5계층 성격도 있어 교재마다 표기가 다릅니다. 시험이나 면접에서는 "암호화는 표현 계층의 역할이고, TLS가 그 일을 한다" 정도로 설명하면 무난합니다.

## 10 7계층 응용 계층 (Application Layer)

**한 줄 답:** 응용 계층은 사용자가 쓰는 프로그램이 네트워크를 이용할 수 있게 해 주는 계층입니다. 브라우저, 메일, 파일 전송 같은 서비스가 쓰는 **프로토콜** 이 여기에 있습니다. 브라우저 프로그램 자체가 아니라, 브라우저가 쓰는 HTTP가 7계층입니다.

| 프로토콜 | 기본 포트 | 하는 일 |
|----|----|----|
| HTTP / HTTPS | 80 / 443 | 웹 페이지와 API 요청·응답 (RFC 9110). HTTP/3는 UDP 443 위의 QUIC을 씁니다. |
| DNS | 53 (UDP, TCP) | 도메인 이름을 IP 주소로 바꿉니다. |
| SMTP / IMAP / POP3 | 25·587 / 143·993 / 110·995 | 메일 보내기와 받기 |
| SSH | 22 | 암호화된 원격 접속 |
| FTP / SFTP | 21 / 22 | 파일 전송 |
| DHCP | 67, 68 (UDP) | 컴퓨터에 IP 주소를 자동으로 나눠 줍니다. |

7계층에서는 **내용** 을 볼 수 있습니다. 어떤 URL을 요청했는지, 어떤 쿠키와 헤더가 있는지, 응답 코드가 무엇인지가 모두 7계층 정보입니다. 그래서 7계층 장비(L7 로드밸런서, WAF, API 게이트웨이)는 "`/api`로 오는 요청은 A 서버로" 같은 세밀한 판단을 할 수 있습니다.

▶ 7계층 요청과 응답을 눈으로 보기

```
# -v: DNS → TCP 연결 → TLS → HTTP 요청·응답 헤더가 순서대로 찍힙니다
curl -v https://example.com -o /dev/null

# DNS(7계층)만 따로 확인
dig +short example.com
nslookup example.com
```

## 11 7계층 한눈에 보는 요약표

**한 줄 답:** 계층마다 주소, 데이터 단위, 장비, 프로토콜이 다르며, 이 표 하나를 기억하면 대부분의 질문에 답할 수 있습니다.

| 계층 | 핵심 역할 | PDU | 주소·식별자 | 장비 | 대표 프로토콜 |
|----|----|----|----|----|----|
| 7 응용 | 서비스 제공 | 데이터 | URL, 도메인 | L7 스위치·LB, WAF, 프록시 | HTTP, DNS, SMTP, SSH |
| 6 표현 | 형식 변환·압축·암호화 | 데이터 | \- | \- | UTF-8, JSON, JPEG, TLS(암호화) |
| 5 세션 | 대화 관리 | 데이터 | 세션 ID | \- | RPC, NetBIOS |
| 4 전송 | 프로세스 간 전달, 신뢰성 | 세그먼트 | 포트 번호 | L4 스위치·LB, 방화벽 | TCP, UDP, (QUIC) |
| 3 네트워크 | 네트워크 간 경로 선택 | 패킷 | IP 주소 | 라우터, L3 스위치 | IP, ICMP, OSPF, BGP |
| 2 데이터링크 | 인접 장비 간 전달, 오류 검출 | 프레임 | MAC 주소 | 스위치, 브리지, AP | 이더넷, 와이파이(802.11), ARP, VLAN |
| 1 물리 | 비트를 신호로 전송 | 비트 | \- | 허브, 리피터, 케이블, 랜카드 | UTP, 광케이블, 전파 |

> 외우는 순서 팁: 아래에서 위로 "물데네전세표응"을 소리 내어 몇 번 읽어 두면 오래 기억에 남습니다.

## 12 주소창에 URL을 치면: 7계층으로 따라가기

**한 줄 답:** 브라우저에 `https://example.com`을 입력하면 DNS 조회(7) → TCP 연결(4) → TLS 협상(5·6) → HTTP 요청(7)이 일어나고, 그 모든 데이터는 IP(3), 이더넷·와이파이(2), 신호(1)를 타고 이동합니다.

1 · DNS (7)

도메인을 IP로 바꿉니다. DNS 질의 자체도 UDP 53번(4) 위로 오갑니다.

2 · ARP (2)

기본 게이트웨이의 MAC 주소를 알아내 첫 구간 프레임을 만들 준비를 합니다.

3 · TCP 연결 (4)

서버 443번 포트로 SYN, SYN+ACK, ACK를 주고받습니다.

4 · TLS (5·6)

인증서를 확인하고 암호 키를 정해, 이후 데이터를 암호화합니다.

5 · HTTP 요청 (7)

GET / 요청을 보내고 HTML 응답을 받습니다. 응답은 gzip 등으로 압축되어 있을 수 있습니다(6).

6 · 라우팅 (3)

패킷은 여러 라우터를 지나며 구간마다 MAC은 바뀌고(2) IP는 그대로 갑니다.

받는 서버 쪽에서는 이 과정이 거꾸로 일어납니다. 랜카드가 신호를 비트로 바꾸고(1), 프레임의 FCS를 검사해 헤더를 떼고(2), IP를 확인하고(3), 포트를 보고 웹 서버 프로세스에 넘기고(4), 암호를 풀고(5·6), 마지막으로 웹 서버가 HTTP 요청을 처리합니다(7).

## 13 계층별로 장애 찾기: 실전 점검 순서

**한 줄 답:** "인터넷이 안 된다"는 문제는 아래 계층부터 하나씩 확인하면 빠르게 범위를 좁힐 수 있습니다.

| 순서 | 확인할 것 | 명령 | 실패하면 의심할 곳 |
|----|----|----|----|
| 1계층 | 링크가 올라왔나 | `ip link`, `ethtool` | 케이블, 포트, 와이파이 신호 |
| 2계층 | 게이트웨이 MAC을 알아냈나 | `ip neigh`, `arp -a` | VLAN 설정, 스위치 포트 |
| 3계층 | 게이트웨이와 외부 IP로 ping이 되나 | `ping`, `traceroute` | IP·라우팅 설정, 방화벽의 ICMP 차단 |
| 4계층 | 목적지 포트가 열려 있나 | `nc -vz host 443`, `ss -tln` | 서버 프로세스 중지, 보안 그룹·방화벽 |
| 5·6계층 | TLS가 맺어지나, 인증서가 맞나 | `openssl s_client -connect host:443` | 인증서 만료, 도메인 불일치, 시스템 시각 |
| 7계층 | HTTP 응답 코드가 정상인가 | `curl -v`, `dig` | DNS 설정, 앱 오류(5xx), 경로 오류(404) |

▶ 한 번에 돌려 보는 계층별 점검 스크립트

```
#!/usr/bin/env bash
# 사용법: ./netcheck.sh example.com
HOST=${1:-example.com}

echo "[L3] 기본 게이트웨이";        ip route | grep default || netstat -rn | grep default
echo "[L3] ping";                  ping -c 2 "$HOST"
echo "[L7] DNS";                   dig +short "$HOST"
echo "[L4] 443 포트";               nc -vz -w 3 "$HOST" 443
echo "[L5/6] TLS 인증서 만료일";    echo | openssl s_client -connect "$HOST:443" -servername "$HOST" 2>/dev/null | openssl x509 -noout -enddate
echo "[L7] HTTP 상태 코드";         curl -s -o /dev/null -w "%{http_code}\n" "https://$HOST"
```

💡 왜 중요할까

이 순서를 몸에 익혀 두면 "서버가 죽었다"는 막연한 말 대신 "3계층까지는 정상이고 443 포트가 닫혀 있다"처럼 정확하게 말할 수 있습니다. 로드밸런서, 방화벽, CDN이 각각 몇 계층에서 일하는지도 이 기준으로 구분합니다.

## 정리

**핵심 1.** OSI 7계층은 통신을 물리, 데이터링크, 네트워크, 전송, 세션, 표현, 응용 7개 역할로 나눈 ISO 표준 참조 모델이며, 각 계층은 자기 일만 하고 바로 아래 계층의 서비스를 이용합니다.

**핵심 2.** 보낼 때는 헤더가 붙고(캡슐화) 받을 때는 떼어집니다. 데이터 단위는 위에서부터 데이터, 세그먼트, 패킷, 프레임, 비트입니다.

**핵심 3.** 주소도 계층마다 다릅니다. 2계층은 MAC(구간마다 바뀜), 3계층은 IP(끝까지 유지), 4계층은 포트(어떤 프로그램인지)입니다. 실제 인터넷은 TCP/IP 4계층으로 동작하지만 장비 분류와 장애 분석에는 OSI 번호를 씁니다.

## 자주 묻는 질문

### OSI 7계층과 TCP/IP 4계층은 무엇이 다른가요?

OSI 7계층은 ISO가 1984년에 발표한 참조 모델이고, TCP/IP 4계층(링크, 인터넷, 전송, 응용)은 실제 인터넷에서 쓰는 구현 모델입니다. TCP/IP는 OSI의 5·6·7계층을 응용 계층 하나로, 1·2계층을 링크 계층 하나로 묶습니다. 장비 분류(L2, L3, L4, L7)에는 OSI 번호를 그대로 씁니다.

### 계층별 데이터 단위(PDU)는 어떻게 되나요?

응용·표현·세션 계층은 데이터(메시지), 전송 계층은 세그먼트(TCP) 또는 데이터그램(UDP), 네트워크 계층은 패킷, 데이터링크 계층은 프레임, 물리 계층은 비트입니다. 일반 이더넷의 MTU는 1,500바이트이고, 여기서 IPv4·TCP 헤더 40바이트를 뺀 1,460바이트가 TCP MSS입니다.

### 스위치와 라우터는 몇 계층 장비인가요?

일반 스위치는 MAC 주소로 프레임을 전달하는 2계층 장비이고, 라우터는 IP 주소로 네트워크 사이의 경로를 고르는 3계층 장비입니다. 라우팅 기능을 갖춘 L3 스위치도 있으며, 포트 번호를 보는 장비는 L4, URL·헤더 같은 내용을 보는 장비는 L7 장비라고 부릅니다.
